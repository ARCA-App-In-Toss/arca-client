## 1. 범위와 관할

### 1.1 이 문서가 소유하는 내용

입력·검증·질문 전환·보관·저장/삭제·복구·피드백·Back/Overlay·포커스·발췌·날짜 형식과 IX·CPY를 소유합니다. 공통 결과는 §4~5, 화면별 조건은 §6, 채택 문구는 §7이 원본입니다.

### 1.2 이 문서가 소유하지 않는 내용

배치는 [03 §3 · L103–123](./03_SCREENS_SPEC.md#3-화면-범위와-추적-지도), 시각 계약은 [02 §9 · L434–573](./02_DESIGN_SYSTEM.md#9-공통-컴포넌트-인벤토리), OP·DTO·오류·서버 판정은 [05 §6 · L207–411](./05_API_SPEC.md#6-도메인-오퍼레이션-계약), 상태·Storage·타이머·플랫폼 어댑터는 [06 §3 · L133–226](./06_FRONTEND_SPEC.md#3-최소-구조와-의존-방향)이 소유합니다. 실제 법무·운영 자료는 §8.1을 따릅니다. 서버가 없다는 이유로 HTTP 상태·필드를 임의로 추가하지 않습니다.

### 1.3 적용 근거

제품 정책·전이는 [Rules · L1–9](../../docs/ARCA_MVP_RULES.md)·[Flow · L1–11](../../docs/ARCA_USER_FLOW.md), 강도는 §3·[00 §7.1 · L143–163](./00_INDEX.md#71-결정-강도와-자율-탐색), 합격 기준과 검증 추적은 §10을 따릅니다.

## 2. 안정 ID와 인용 규칙

| 대상 | 형식 | 예시 | 소유 문서 |
|---|---|---|---|
| 상호작용 계약 | `IX-###` | `IX-008` | 이 문서 |
| 공통 문구 | `CPY-COM-###` | `CPY-COM-005` | 이 문서 |
| 화면 문구 | `CPY-F{화면}-###` | `CPY-F11-018` | 이 문서 |

- `IX-*`는 사건과 결과의 의미가 같으면 화면이 달라도 재사용합니다. 의미가 달라지면 새 ID를 만들며 폐기된 번호를 재사용하지 않습니다.
- `CPY-*`는 문구의 안정 ID입니다. 각 문구의 필수 의미는 §7 용도 열, 표시 조건은 해당 상태의 §6·§7.0, 권장 문장은 §7의 현재 채택 문자열로 정의합니다. 구현은 채택 문자열을 사용하며 의미·조건을 유지하는 축약·어미 조정은 §7.0의 자율 조정 범위입니다. 채택 후 문구와 검증 기준을 같은 변경에서 동기화합니다. 동적 값은 `{camelCase}` 자리표시자로 표시하며 API 필드명을 뜻하지 않습니다.
- 보이는 문구와 접근성 이름이 같아도 역할이 다르면 각각 ID를 둘 수 있습니다. 하나의 문구가 여러 화면에서 완전히 같은 의미로 쓰이면 공통 ID를 참조할 수 있습니다.
- 폐기 ID는 번호만 예약하며 화면·접근성 API에 문자열을 전달하지 않습니다. 다른 문서의 IX-010 참조는 IX-036으로 읽습니다.
  - IX-010·019·038
  - CPY-F01-007~012, CPY-F02-003~005, CPY-F03-016
  - CPY-F10-002·010·012~014·017·018·037, CPY-F11-043
  - CPY-F12-002·003·005·007·009~011·015·016, CPY-F13-011
  - CPY-F20-002·006·012·013·016·023·024, CPY-F21-006·007
  - CPY-F22-005, CPY-F23-002~004, CPY-F30-023·024, CPY-F31-003·005

## 4. 공통 입력과 문자열 처리

### 4.1 입력·IME·문자 수 — IX-001·IX-002

| 항목 | 닉네임 F03·F30 | 응답 F11·F22 |
|---|---|---|
| 입력 형태 | 한 줄 | 여러 줄 |
| 허용 길이 | 앞뒤 공백 제거 뒤 0자 또는 2~12자 | 원문 그대로 1~2,000자 |
| 문자 단위 | Unicode 확장 grapheme cluster | Unicode 확장 grapheme cluster |
| 이모지 | 결합된 화면상 이모지 1개를 1자로 계산 | 동일 |
| 줄바꿈 | 허용하지 않음 | 한 논리적 줄바꿈을 1자로 계산 |
| 공백 | 내부 공백 허용, 제출 직전 앞뒤 공백 제거 | 앞뒤·연속·공백 전용 입력 모두 보존·계산 |
| 붙여넣기 | 허용, 초과·금지 문자를 자르지 않음 | 허용, 초과 원문을 자르지 않음 |
| 상한 초과 | 입력 유지, 저장·진행 비활성 | 입력 유지, 저장 비활성 |
| 빈 값 | F03은 정상 건너뛰기, F30은 저장 시 닉네임 해제 | 오류 없이 저장만 비활성 |

카운터는 IME composition 중에도 현재 input/textarea 값의 Unicode 확장 grapheme 수를 즉시 표시합니다. 닉네임 카운터만 앞뒤 공백을 제외하고 응답 카운터는 공백·개행을 그대로 셉니다. 숫자 갱신은 blur·debounce·`compositionend`를 기다리지 않으며 매 입력 live announcement를 만들지 않습니다. 오류·제출 가능 판정은 마지막 조합 완료값을 유지하고 `compositionend`에서 확정합니다. 조합 중 저장·진행 실행과 임시 보관 commit은 막습니다. 닉네임의 Enter는 조합 중이 아닐 때 현재 Primary와 같은 결과를 실행합니다. 응답 Textarea의 Enter는 줄바꿈이며 저장 단축키를 새로 만들지 않습니다.

응답 원문은 표시·임시 보관·서버 저장·복사·상세에서 trim, Unicode 정규화, 연속 공백 축약, 빈 줄 제거, 문장 재작성 없이 왕복해야 합니다. 전송 계층의 개행 표현과 서버 검증값은 `05`가 정의하되 사용자가 확인한 원문을 바꾸면 안 됩니다.

외부 입력 컴포넌트를 사용해도 위 의미·노출 조건을 유지합니다. 기본 글자 수·자동 절단·조합 중 검증·helper 숨김·live 발표가 이 계약을 덮어쓰지 않도록 [06 §10.6 · L653–659](./06_FRONTEND_SPEC.md#106-선별-입력상태-컴포넌트-연결)에서 연결합니다(D-TECH-052). 시각 교체는 기존 IX·CPY ID를 유지합니다.

### 4.2 검증 발생·해제

- 닉네임 금지 문자·12자 초과는 IME 조합 종료 뒤 즉시 표시합니다. 1자는 blur 또는 진행·저장 시도 시 표시합니다.
- 닉네임 오류는 값이 유효해지거나 빈 값이 되면 즉시 해제합니다. F03의 빈 값은 저장 요청 없이 진행하며 F30의 빈 값 저장은 저장된 닉네임을 해제합니다.
- 응답 0자는 오류를 표시하지 않습니다. 2,000자 초과는 조합 종료 뒤 즉시 표시하고 `{overCount}`가 0이 되면 해제합니다.
- 오류가 있는 동안 실행은 차단하되 입력·선택·복사·Back은 유지합니다. 실행을 시도했는데 아직 발표하지 않은 오류가 있으면 첫 오류를 한 번 알리고 입력으로 포커스를 강제로 이동하지 않습니다.
- 카운터와 서버 판정은 같은 grapheme 의미를 사용해야 합니다. 구체 라이브러리와 서버 합의는 `05`·`06`에 인계합니다.

### 4.3 닉네임 진행·편집 — IX-003·IX-004

- IX-003: F03의 빈 닉네임은 요청 없이 진행하고 유효한 닉네임은 저장 성공 뒤 F10으로 이동합니다. 입력 검증은 IX-001~002, 확정 실패 뒤 명시적 건너뛰기는 IX-035를 따릅니다.
- IX-004: F30은 현재 닉네임으로 편집을 시작하고 정규화된 값이 같으면 저장을 비활성화합니다. 입력 아래 한 줄에 검증 오류(왼쪽)와 글자 수(오른쪽)만 보이고, 빈 값 안내(CPY-F30-010)와 변경 없음(CPY-F30-017)은 입력의 접근성 설명으로만 제공합니다(D-UI-101). 빈 값 저장 성공은 닉네임 해제, 취소는 편집값 즉시 폐기와 실행 요소 포커스 복원입니다. 별도 임시본은 만들지 않습니다.

## 5. 공통 상호작용 계약

### 5.1 기기 임시 보관 — IX-005

| 사건·선행 조건 | 사용자 조작과 잠금 | 보이는 결과·보존 | 피드백·포커스·종료 | 추적 |
|---|---|---|---|---|
| F11 입력 변경 | 계속 입력 가능. 실제 쓰기 중에도 커서를 가리지 않음 | 날짜·질문별 본문과 마지막 수정 시각을 보관. 성공 확인 전 완료 표시 금지 | Field help에 보관 중→성공. 정상 반복 성공은 live 발표하지 않음 | AN-02·04, Acc #12·14·36 |
| F22 입력 변경 | F11과 동일 | 응답별 수정 임시본을 원 서버 본문과 분리 | 복원·실패만 한 번 발표 | AN-02·04·07, Acc #19·36 |
| 로컬 쓰기 실패 | 입력·질문·커서 유지 | 현재 화면의 본문은 지우지 않고 미보관 상태 표시 | InlineStatus, 재시도. 성공하면 실패 종료 | AN-04, Acc #14·17 |
| 보존 기간 만료 | 별도 조작 없음 | 마지막 수정 후 정확히 7일이 지나면 해당 임시본 제거 | F13에서 만료 상태, 오늘 이동 | AN-02, Acc #15·18 |
| 최초 서버 저장 성공 | 없음 | 같은 날짜 배포 단위의 교체 전 콘텐츠를 포함한 모든 질문 임시본 제거 | F12 전이 뒤 재노출 금지 | AN-02, Acc #13 |
| 수정 저장 성공 | 없음 | 해당 수정 임시본 제거 | F21 갱신 | AN-02·07, Acc #19·33 |

보관 시점·debounce/maxWait·Storage key·교대 사본·청소 작업은 `06`이 소유합니다. 연속 입력에도 완료된 문자열의 보관 요청이 무기한 밀리지 않게 하며 IME 조합 중 commit 확정 금지는 유지합니다. 앱 강제 종료를 확인 Dialog로 보호한다고 보장하지 않으며, 실제 Storage 쓰기 성공을 입력 중 지속적으로 확인하는 구현이 필요합니다.

### 5.2 질문 전환 — IX-006

1. 기본↔대체 질문 전환을 선택하면 현재 질문의 최신 본문 쓰기 결과를 먼저 확인합니다.
2. 성공하면 질문을 즉시 전환하고 대상 질문의 임시본을 조회·복원합니다. 매번 확인 Dialog를 열지 않습니다.
3. 실패·결과 미확인이면 질문을 바꾸지 않고 현재 본문·커서·스크롤을 유지합니다.
4. 포커스는 전환 조작에 남기고 접근성 이름을 다음 가능한 행동으로 바꿉니다. 결과는 하나의 polite 알림으로 전달합니다. F10은 새 질문 전문을 담은 CPY-F10-035, F11은 CPY-F11-015 또는 대상 질문의 임시본을 복원했을 때 CPY-F11-012입니다. Textarea를 자동 포커스하거나 키보드를 열지 않습니다.
5. 전환 애니메이션은 입력 가능 시점을 늦추지 않습니다. Reduced Motion에서는 같은 내용으로 즉시 교체합니다.

### 5.3 작성 화면 이탈 — IX-007

| 현재 상태 | Back·앱 내부 이동 결과 |
|---|---|

| 최신 변경의 로컬 쓰기 성공 | 확인 없이 이동, 재진입 시 복원 |
| 로컬 쓰기 진행 중 | 유한한 대기 뒤 성공이면 이동. 실패·계속 미확인이면 미보관 이탈 확인으로 전환하며 무기한 보류하지 않음 |

이탈 확인의 안전 행동은 작성 유지, 위험 행동은 화면 이탈입니다. Dialog 실행 전 Android Back·Escape는 안전한 취소와 같고 외부 영역 탭으로는 닫지 않습니다.

### 5.5 피드백 선택·우선순위 — IX-013·IX-014

| 우선순위 | 상태 | 기본 표현 |
|---:|---|---|
| 1 | 실행 전 삭제·이탈 확인, 실행 중 삭제 | Dialog |
| 2 | 날짜 변경·현재 저장 불가·저장 결과 미확인 | 전용 상태 또는 입력 가까이 InlineStatus |
| 3 | 서버 저장 실패·세션 복구 실패 | 실행 위치 InlineStatus |
| 4 | 기기 임시 보관 실패 | Field 가까이 InlineStatus |
| 5 | 화면·목록의 부분 조회 실패 | 실패한 영역 InlineStatus |
| 6 | 행동이 필요 없는 성공·정보 | Toast 또는 정적 상태 |

- 같은 입력 영역에는 가장 높은 유효 상태를 주 안내로 표시합니다. 로컬 보관 실패·미확인처럼 현재 유실 위험과 다음 행동을 바꾸는 정보는 IX-037에 따라 같은 안내 안에 즉시 결합합니다. 그 밖의 낮은 상태는 높은 상태 종료 뒤 여전히 유효할 때 다시 표시합니다.
- 차단 Dialog가 열려 있으면 새 Toast를 겹치지 않습니다. Dialog가 닫힌 뒤에도 의미가 남는 결과만 한 번 전달합니다.
- 같은 사건을 InlineStatus와 Toast로 중복 알리지 않습니다. 화면 전체에 하나의 조정된 live region을 사용합니다.
- InlineStatus는 원인이 해제되거나 재시도가 성공할 때까지 유지합니다. 재시도 중에는 진행 상태로 교체하며 실패하면 갱신합니다.
- F02 탑승·F03 닉네임 저장·F11 응답 저장의 진행 문구, F11 대기 중 보조 행동(복사·`나중에 확인하기`), 삭제 확인 Dialog(F23·F31 2차)의 진행 문구는 요청이 0.5초 넘게 이어질 때만 표시합니다. 그 전에는 Primary의 처리 중 표시(`aria-busy`)만 둡니다. 성공으로 화면을 떠나는 동안에도 처리 중 표시를 유지합니다. read-only·중복 실행·Dismiss 잠금은 즉시 적용하고, 결과 미확인·실패 안내는 지연하지 않습니다(D-UI-104). F22 수정 저장과 F30 닉네임 저장의 진행 문구·보조 행동은 지연 없이 표시합니다.
- StatePanel은 신뢰할 Data가 없는 전체 Loading·Error·Empty에만 사용하며 재시도 또는 전이까지 유지합니다.
- Toast는 행동이 없는 성공·정보에만 사용합니다. 기본 노출은 4초이며 포커스를 받지 않고, 같은 사건의 반복은 하나로 합칩니다. 이 시간은 실기기 접근성 검증 뒤 조정할 수 있습니다.
- Dialog·Sheet는 자동 종료하지 않습니다.

### 5.6 Overlay — IX-015·IX-016

| 입력 | PixelSheet | 삭제·이탈 PixelAlertDialog | Mutation 시작 뒤 Dialog |
|---|---|---|---|
| 명시적 닫기·취소 | 종료 | 안전한 취소 | 비활성 |
| 외부 영역 탭 | 종료 | 종료하지 않음 | 종료하지 않음 |
| Android Back | 종료 | 안전한 취소 | 잠금 |
| Escape | 종료 | 안전한 취소 | 잠금 |
| swipe | 제공하지 않음 | 해당 없음 | 해당 없음 |

Overlay는 열릴 때 내부 첫 의미 요소로 포커스를 옮기고 배경을 스크린 리더와 포인터에서 비활성화합니다. Sheet는 제목 또는 첫 행, 비가역 Dialog는 안전한 취소가 초기 포커스입니다. 정상 종료하면 실행 요소와 배경 스크롤을 복원합니다. 파괴 실행 성공으로 라우트가 바뀌면 새 화면 제목으로 이동합니다.

외부 Dialog/Sheet의 외형을 적용해도 위 닫힘·초기/복귀 포커스 계약을 우선합니다. 자동 닫기·내부 pending 상태가 저장/삭제 판정을 대신하지 않으며 공통 Radix 연결은 [06 §10.1 · L606–616](./06_FRONTEND_SPEC.md#101-dialogsheet-wrapper)이 소유합니다(D-TECH-052).

### 5.7 Back·키보드·포커스 — IX-017·IX-018

Back 처리 순서는 다음과 같습니다.

1. Mutation 중인 Dialog이면 닫지 않음. 키보드 닫기로 Dialog 취소·화면 이탈을 함께 실행하지 않음
2. 그 밖의 열린 Overlay는 IX-015·IX-016 규칙으로 종료·취소
3. 작성 화면의 입력 키보드가 열려 있으면 저장·결과 확인 중에도 키보드만 닫고 같은 입력·화면 유지
4. 키보드가 닫힌 F11·F22는 요청 대기·결과 미확인 모두 IX-008/036의 보관 조건으로 이탈 판정, 그 밖의 미보관 최신 변경은 IX-007 적용
5. 그 밖에는 화면 계층에 따라 이전 화면으로 이동
6. F10·F20·F30 루트는 앱인토스 내비게이션·플랫폼 종료 정책을 따르며 앱 내부 Back을 중복 표시하지 않음. 루트 탭 이동은 히스토리에 쌓이므로 Android Back은 직전 탭으로 돌아갈 수 있음

라우트 전이 뒤에는 새 `ScreenTitle`에 프로그래밍 포커스를 둡니다. 예외는 다음과 같습니다.

- 질문 전환: 전환 조작 유지, 새 질문 live 발표
- F12 완료: 완료 결과 heading
- Overlay 종료: 실행 요소 복원
- 외부 약관·고객센터 복귀: 실행 요소와 스크롤·선택·편집 상태 복원
- 정보 재조회: 이미 읽던 위치와 포커스를 이동하지 않음. F20의 `맨 위로`만 IX-042의 상단 이동과 목록 제목 포커스

같은 방문의 질문 선택·selection·scroll·복귀 대상은 [06 §5.6 · L343–351](./06_FRONTEND_SPEC.md#56-navigationcontext의-수명과-복원)의 메모리 NavigationContext로 복원합니다. 본문·revision/editVersion 확인 뒤 적용하고 정보 재조회가 편집 중인 상태를 덮지 않습니다. 키보드를 자동으로 다시 열지 않으며 주체/권한/generation 변경·삭제 때 과거 문맥을 폐기합니다.

### 5.10 발췌·날짜·동적 값 — IX-027·IX-028

**응답 발췌**

다음은 현재 채택한 **조정 가능한 표시 기본값**입니다. 프로필 이름은 화면·숫자와 독립적이며 API enum은 수치 조정으로 바꾸지 않습니다.

| 프로필 | 현재 EGC 상한 | 현재 논리적 줄 상한 | 현재 선택 화면 |
|---|---:|---:|---|
| COMPACT | 96 | 4 | OP-008 호환 응답·캐시 유지; F12 화면에는 발췌 미표시(D-UI-102) |
| STANDARD | 120 | 4 | OP-010 호환 응답·캐시 유지; F20 화면에는 발췌 미표시 |
| EXPANDED | 160 | 6 | OP-005 호환 응답·캐시 유지; F10 화면에는 발췌 미표시(OD-28) |

프로필 예산·화면별 선택은 원문 prefix·비공개·상세 접근·실제 생략 의미를 유지하고 320px·200% 글자·키보드/스크린 리더에서 읽기·이동 결과를 비교해 조정할 수 있습니다. 채택값과 근거를 이 표에 반영하고 서버 배포 설정·합성 fixture를 함께 맞춥니다. FE는 응답의 실제 limits를 사용하며 기존 수치를 별도 하드코딩하지 않습니다. API 전체 본문·행별 상세 조회를 추가하지 않습니다.

1. 저장된 자기 응답의 시작부터 이어지는 가장 긴 연속 prefix만 사용합니다.
2. grapheme 또는 논리적 줄 상한 중 먼저 도달한 경계에서 자릅니다. 빈 줄도 한 줄로 세며 공백·줄바꿈을 `pre-wrap` 의미로 보존합니다.
3. 앞뒤 공백 제거, 연속 공백·빈 줄 축약, AI 요약·재작성·감정 해석을 하지 않습니다.
4. 실제 원문이 일부 빠졌을 때만 데이터 밖 UI 생략 기호 `…`를 붙이고 Label을 `내 답변 일부`로 표시합니다. 전문이 모두 들어가면 생략 기호 없이 `내 답변`으로 표시합니다.
5. 생략 기호는 저장·복사·상세 원문에 포함하지 않습니다. 원문이 공백만 포함하면 빈 원문 영역을 유지하고 `공백만 포함된 응답이에요.`를 보조 설명으로 제공합니다.
6. F20의 질문 일부는 시작부터 80 grapheme·2개 논리적 줄을 권장 기본값으로 사용하고 같은 생략 규칙을 적용합니다. F01·F10·F11·F13·F21·F22의 질문 전문은 자르지 않습니다.
7. 전달 필드·서버/클라이언트 절단·수정/삭제 갱신 계약은 `05`가 소유합니다. 행마다 상세 조회하는 구조를 전제하지 않습니다.

| `{dateKst}`, `{createdDateKst}`, `{draftDateKst}` | `2026년 9월 12일` | 필수 날짜가 없으면 해당 Data를 완성 상태로 표시하지 않음 |

| `{year}`, `{month}` | 각각 단위 없는 정수 `2026`, `9`; 문구에서 연·월 구성 | 실제 KST 작성 연월만 사용 |
| `{memoryCount}`, `{loadedCount}` | 단위 없는 정수. 문구 삽입 시 `1,234`처럼 천 단위 쉼표 | 미확인 수를 `0`으로 표시하지 않음 |
| `{currentScene}`, `{totalScenes}` | 단위 없는 양의 정수 | 현재 장면과 전체 장면을 모두 확인한 뒤 함께 표시 |
| `{currentCount}` | 단위 없는 현재 글자 수 `124`; 전체 표시는 문구가 구성 | 조합 중에도 현재 입력값으로 즉시 갱신; 검증·보관 확정과 분리 |
| `{overCount}` | 단위 없는 초과 글자 수 `3` | 0이면 초과 오류 해제 |
| `{questionText}`, `{responseText}` | 확인된 질문·응답 원문 | 공백·줄바꿈을 바꾸지 않으며 필수 원문이 없으면 완성 상태로 표시하지 않음 |
| `{questionExcerpt}`, `{responseExcerpt}` | 이 절의 원문 prefix·생략 규칙을 적용한 값 | 원문 대신 임의 요약·대체 문구를 만들지 않음 |
| `{displayName}` | 닉네임이 있으면 닉네임, 없으면 승객 코드 | 원본 익명 식별키나 임의 호칭으로 대체 금지 |
| `{semaCode}` | 서버가 제공한 안전한 표시 코드 | 없으면 임의 코드 생성 금지 |
| `{passengerCode}` | 서버가 제공한 승객용 표시 코드 | 원본 익명 식별키로 대체 금지 |
| `{safeErrorId}` | 민감값 없는 오류 식별 코드 | 없으면 영역·복사 행동 함께 숨김 |
| `{appVersion}` | 배포 버전 문자열 | 빌드가 제공한 값 사용, 임의 버전 금지 |

완결된 설명·상태·오류 문장에는 마침표를 붙이고 제목·Label·버튼에는 붙이지 않습니다. 일반 UI는 존댓말, 인트로 편집본은 원문의 서술 호흡을 사용합니다.

### 5.11 결과 동기화 — IX-029

- F11에 있는 동안 확인한 최초 저장 성공만 F12 연출 자격을 갖습니다. 이미 이탈한 뒤 확인한 성공은 IX-036에 따라 강제 이동·연출 없이 동기화합니다. F22 수정 저장과 정보 재조회에는 연출·햅틱을 실행하지 않습니다.
- F22 수정 성공 뒤 F21 전문과 F10 발췌·F20 캐시를 갱신합니다. F20 화면에는 변하지 않는 질문·날짜만 남으며 다시 연 상세에서 수정 본문을 읽습니다.
- F23 삭제 성공 뒤 F20 행·빈 월 제목·누적 수를 갱신하고 관련 F10·F12 발췌 캐시를 제거합니다.
- F31 성공 뒤 응답·발췌·임시본·승객 세션이 브라우저 히스토리나 캐시에서 다시 나타나지 않아야 합니다. 제한 결과 확인 세션의 ack 순서는 [05 §6.7 · L341–373](./05_API_SPEC.md#67-op-007009-공통-command-lifecycle)을 따르며 ack 실패만으로 최초 탑승 이동을 막지 않습니다.
- 다른 기기의 ack는 최소 proof를 지우지 않습니다. 과거 성공 후 수정/삭제된 답변은 옛 revision의 발췌로 보강하지 않고 현재 resource를 조회합니다. 이전 generation의 늦은 결과는 새 탑승의 캐시를 지우거나 덮지 않습니다.
- 보조 조회 실패는 이미 확인된 저장·수정·삭제 성공을 취소하지 않으며 같은 Mutation을 반복하지 않습니다.

### 5.13 선택형 닉네임 실패 진행 — IX-035

- F03의 정상 진행은 하나의 `첫 질문 만나기`입니다. 확정된 닉네임 저장 실패 또는 오프라인으로 요청을 보내지 못한 상태에서만 `CPY-F03-019`를 Secondary로 추가합니다.
- 사용자가 선택하면 실패한 편집값을 폐기하고 닉네임 저장·해제 요청 없이 F10으로 이동합니다. 이미 생성된 승객과 승객 코드를 유지합니다. 실패 자체만으로 자동 이동하지 않습니다.
- 저장 요청 중에는 이 행동도 잠그며, 결과 미확인을 확정 실패로 간주하지 않습니다. 재시도·입력 수정·직접 비우기는 계속 지원합니다. F30에는 이 진행 행동을 추가하지 않습니다.

닉네임 응답 유실은 05 OP-004의 같은 operation ID·입력으로 적용 receipt를 복원합니다. 현재 profile과 과거 receipt는 구분하고 다른 기기의 최신 값을 과거 값으로 덮지 않습니다. nickname 결과 보존이 만료되면 해당 key가 추가 실행되지 않는다는 서버 거절을 확인하고 현재 profile로 편집 문맥을 갱신합니다. 과거 저장을 성공/실패로 추정하지 않으며 다음 저장은 새 사용자 행동·최신 revision으로 수행합니다. F02는 생성 성공 응답의 ACTIVE 세션을 사용하며 응답 유실은 같은 생성 ID로 복구합니다.

### 5.14 저장 결과 확인과 안전한 이탈 — IX-036

적용 대상은 F11 최초 저장과 F22 수정 저장이며, 제품 기준은 Rules AN-09입니다.

1. 서버 저장이나 결과 조회는 무기한 진행 상태에 머무르지 않습니다. 조회 cycle 상한의 시작값은 10초이며 06에서 조정·검증합니다. 이는 화면 잠금 시간이 아닙니다. 아래 보관 조건을 충족하면 cycle 중에도 이탈할 수 있으며 시간 경과 자체는 실패/미저장의 증거가 아닙니다(OD-21).
2. 저장 요청의 결과가 불확실하면 비변경 결과 조회를 우선합니다. 이 조회도 실패·시간 초과하거나 서버가 처리 중이라고 응답하면 정적인 결과 미확인 상태로 전환합니다. 새 요청 ID로 저장하지 않으며, ticket 응답 유실은 [05 §6.4 · L280–309](./05_API_SPEC.md#64-op-006-prepareanswerwrite)의 같은 ID·입력 재전송으로 복원합니다. PREPARED일 때만 정확한 원 payload로 같은 ticket 실행을 이어갈 수 있습니다. `결과 다시 확인하기`·복사·보관 재시도를 제공합니다. 키보드 닫기는 항상 유지합니다.
3. 최신 본문과 같은 요청을 다시 식별·복구할 추적 상태의 기기 쓰기 성공을 모두 확인하면 결과 대기 중에도 `CPY-F11-040`과 화면 Back으로 이탈할 수 있습니다. ticket 수신 전에는 같은 operation ID·고정 입력으로 준비 결과를 복원할 수 있어야 하고 수신 뒤에는 ticket 보관도 확인합니다. 구체 phase별 확인값은 [06 §8.6 · L530–540](./06_FRONTEND_SPEC.md#86-안전-이탈과-본문-만료)을 따릅니다. F11은 F10, F22는 F21로 돌아갑니다. 이탈은 요청 취소·성공·실패를 뜻하지 않습니다. F22도 공통 이탈·보관 재시도 문구 CPY-F11-040~042를 사용합니다.
4. 두 보관 중 하나라도 실패·미확인이면 안전하게 보관됐다고 안내하지 않습니다. 같은 상태에서 원문·직접 선택·복사·보관 재시도를 유지하고, 앱 종료 전 복사를 안내합니다. 본문 보관 성공과 요청 추적 상태 보관 성공은 서로 대체하지 않습니다. 요청 대기·결과 미확인 동안 앱 내부 안전 이탈은 두 보관을 확인한 경우에만 제공합니다. 플랫폼 강제 종료를 막거나 복사 성공만으로 기기 보관을 보장하지 않습니다.
5. 이탈 후 F10에서는 CPY-F10-038~039, F21에서는 CPY-F21-017~018로 해당 작성 화면에 다시 접근할 수 있습니다. 같은 날짜 배포 단위·응답의 새 저장·질문 전환·수정 폐기·개별 삭제는 미확인 요청을 해결할 때까지 막습니다. 다른 기록 읽기·설정·플랫폼 이동은 유지합니다. 서버 상태 확인이 평범한 Data 화면이나 새 작성 화면보다 먼저 적용됩니다.
6. 재진입·재실행 시 본문과 추적 상태를 복원한 뒤 같은 요청의 결과를 먼저 조회합니다. 확정 성공이면 원문·발췌를 동기화하고 관련 임시본을 제거합니다. F11에 머물러 확인한 최초 성공만 정상 F12로 전이하며, 이미 다른 화면에 있으면 강제 이동·연출 없이 한 번의 성공 알림과 관련 정보 갱신으로 끝냅니다. F22에 있는 동안 확인한 수정 성공은 F21로 이동하고, 이미 다른 화면에 있으면 현재 문맥에서 원문을 동기화합니다.
7. 미저장 확정은 원 요청이 나중에 적용되지 않는다는 서버 보장까지 포함합니다. 단순 조회 실패·기록 부재·타임아웃으로 판단하지 않습니다. 미적용 확정 또는 IX-041의 인증된 종료·최신 상태 확인 뒤 현재 상태에 따라 편집·수동 재저장을 열고, 날짜 변경·SEMA 중지는 현재 제품 규칙으로 다시 판정합니다. 같은 요청의 지연 응답이나 재조회로 저장·완료 알림을 중복 실행하지 않습니다.
8. 임시본문의 7일 만료는 유지합니다. 만료 뒤 원문을 복원하지 않고 결과 확인에 필요한 최소 추적 상태만 미확인 동안 유지합니다. 성공/미적용 확인·IX-041의 인증된 종료 정리 또는 전체 삭제 성공 시 추적 상태를 제거하며, 늦은 응답이 삭제된 세션·캐시·본문을 되살리지 않게 합니다. 구체 추적값·API·만료 청소·동시성은 `05`·`06`이 정의합니다.

### 5.14.1 준비 요청 종료·과거 결과 정리 — IX-041

IX-036을 보완합니다. 정상 저장의 진행 표시에는 PREPARED/EXECUTING 같은 구현 용어를 노출하지 않습니다.

| 서버 확인 상태 | 사용자 행동·결과 | 문구 |

| PREPARED이며 원 payload가 없거나 사용자가 종료하려 함 | 명시적 요청 종료 → OP-015. NOT_APPLIED 확인 뒤 입력 유지·잠금 해제. 이미 실행 중이면 결과 확인 유지 | CPY-COM-020·021 |
| CLOSED_OUTCOME_UNAVAILABLE | 과거 결과 미확인 안내 → 명시적 정리 → OP-015의 추가 실행 불가·현재 상태 확인 뒤 추적 제거 | CPY-COM-022·023 |
| 정리 결과 현재 답변 존재 | 최신 상세·revision으로 이동/조회. 이전 임시본으로 덮거나 성공 연출하지 않음 | CPY-COM-024 |
| 정리 결과 오늘 신규 작성 가능 | 남은 입력을 유지하고 새 사용자 저장에만 새 요청 사용 | CPY-COM-025 |

### 5.14.2 기록 목록의 상단 갱신 — IX-042

깊은 목록의 읽던 위치를 바꾸는 최신 first-page 후보는 안내·행동 없이 보류하고, 사용자가 맨 위로 돌아왔을 때 적용합니다(D-UI-105). 원인·후보 수명·chain 교체는 [06 §6.3 · L378–395](./06_FRONTEND_SPEC.md#63-f20-page-chain과-누적-수)이 소유합니다. 새 기록의 개수·존재를 추정하지 않습니다.

- 후보 준비: 화면·발표 없음. 기존 행·scroll·focus 유지, Toast/자동 스크롤 없음.
- 맨 위로(CMP-026): 한 화면 높이 넘게 내렸을 때만 루트 탭 위 오른쪽에 나타남. 누르면 맨 위로 스크롤하고(Reduced Motion은 즉시) 목록 제목에 포커스.
- 현재 루트 탭 다시 누르기: F10·F20·F30 모두 같은 방식으로 맨 위로 스크롤하고 포커스는 탭에 그대로 둠.
- 맨 위 도달(직접 스크롤 또는 `맨 위로`): 적용 가능한 후보면 최신 chain으로 교체하되 포커스를 다시 옮기지 않음. 기존 tail과 섞지 않음.
- 후보 실패/만료·mutation/주체/generation 변경: 낡은 후보 폐기, 기존 유효 목록과 오류별 재조회 유지.

### 5.15 복합 오류의 보존 정보 — IX-037

- 우선순위는 주 안내를 정하는 기준입니다. 상위 오류가 유효해도 최신 본문의 기기 보관 실패·미확인과 복사 필요성은 숨기지 않습니다. 하나의 InlineStatus 안에서 주요 문제→보관 상태→필요한 행동 순서로 결합하고 live 발표도 한 번만 합니다.
- 기기 쓰기 성공을 확인한 경우에만 보관 성공 문구를 사용합니다. 보관 중·결과 미확인에는 `CPY-COM-008`을 함께 사용하고, 실패로 확정되면 해당 실패 문구로 바꿉니다. 미보관 이탈 경고와 복사 경로를 유지합니다.
- F11 결과 미확인은 CPY-F11-026 또는 027, 오프라인은 030 또는 031을 사용합니다. F22 결과 미확인은 CPY-F22-020에 029 또는 030을 결합하고, 오프라인은 022 또는 031을 사용합니다. 보관 미확인에는 이 성공/실패 완성 문구를 쓰지 않고 서버 상태만 전달하는 CPY-COM-009 또는 CPY-F11-044/F22-020에 CPY-COM-008을 결합합니다. 서버 저장 실패는 CPY-F11-020/F22-016에 보관 실패 CPY-F11-013/F22-012 또는 보관 미확인 CPY-COM-008을 결합합니다. F11 SEMA 운영 중지는 CPY-F11-033/034이며 보관 미확인이면 CPY-F11-020에 CPY-COM-008을 결합합니다. 결과 보존 만료는 CPY-COM-022에 같은 보관 문구를 결합합니다.
- 서버 저장 상태와 본문 기기 보관 상태, 결과 재조회용 추적 상태를 각각 판단합니다. 본문은 보관됐으나 추적 상태만 실패한 경우 CPY-F11-042를 사용합니다. 연결 복귀는 서버 저장 성공을 뜻하지 않으며 미저장 상태·수동 저장 행동을 유지합니다.

### 5.17 완료 결과와 행동 고정 — IX-039

- 서버 성공 직후 F12 연출을 시작하고 완료 heading CPY-F12-004는 누적 수 조회와 무관하게 유지합니다. F10 완료에도 확인된 저장 결과 CPY-F10-011을 유지합니다. 수 확인 실패 문구는 조회 실패만 전달합니다.
- F12의 두 이동 버튼이 처음 조작 가능해지는 순간 확인된 수로 위계를 한 번 결정합니다. 1개는 기록 우선, 2개 이상은 오늘 우선, 미확인은 오늘 우선입니다. 버튼을 조작 가능하게 하는 시점을 조회 때문에 늦추지 않습니다.

### 5.18 복사 실패의 직접 선택 안내 — IX-040

- F11·F13·F22에서 복사 실패 또는 권한 거부 시 원문을 유지하고 직접 선택 방법을 화면에도 표시합니다. 포커스는 read-only 원문으로 옮기고 자동 전체 선택은 하지 않습니다.

## 7. UI 문구 카탈로그

### 7.0 필수 의미·표시 조건·권장 문장

각 활성 CPY의 계약은 다음 세 축으로 읽습니다. 용도 열은 전달해야 할 필수 의미·대상, 해당 화면의 §6 상태·사건은 표시 조건, 실제 문구 열은 현재 채택한 권장 문장입니다. Label·제목·값은 해당 요소가 표시될 때, 행동 문구는 그 행동이 제공될 때 사용합니다. 성공·실패·진행 문구는 이름이 가리키는 결과를 실제로 확인한 상태에서만 사용합니다. 접근성 전용 이름·발표는 지정한 접근성 API에 전달하며 시각 문구의 필수 대체 행동을 숨기는 용도로 쓰지 않습니다.

- 화면에 유지된 입력·목록과 가까운 재시도 행동으로 이미 전달하는 설명은 반복하지 않습니다. 오류의 대상·원인과 유실 위험·다음 행동은 유지합니다. 입력 상한은 카운터에 항상 표시하고 초과 문구는 줄일 글자 수를 안내합니다.
- 의미와 표시 조건을 보존하는 중복 설명 삭제·어미·호칭 조정은 자율적으로 비교·채택할 수 있습니다. 각 문장마다 사전 승인을 요구하지 않으며 채택 문자열·근거·관련 스냅샷을 같은 변경에서 갱신합니다. 원문 서사, 필수 고지 항목·기간, 저장 결과, 삭제 범위·복구 가능성, 유실 위험, 행동·접근성 의미 변경은 이 범위에 포함하지 않습니다.
- 하네스는 현재 채택 문자열의 사용과 함께 필수 의미·상태 조건·행동 도달성·입력 보존을 검증합니다. 탐색 중 과거 문장과의 문자 일치만으로 의미가 보존된 대안을 실패 처리하지 않습니다. 배포 시 채택 문자열은 결정적으로 사용하며 실행마다 임의로 생성하지 않습니다.
- `응답`은 도메인 문서·API의 용어로 유지하고 일반 UI Label은 `내 답변`, 실제 발췌는 `내 답변 일부`, 작성 행동은 `답변 작성하기`, 작성 화면 제목은 `답변 쓰기`로 통일합니다. 서버 저장 완료된 대상은 `기억 조각`으로 부릅니다.
- 숫자 자리표시자는 단위 없는 수입니다. `개`·`자`, 분모와 `/`는 문구에서 한 번만 붙이며 `{memoryCount}`·`{loadedCount}`의 천 단위 쉼표만 포맷합니다. 예: `기억 조각 1,234개`, `3자를 줄여 주세요.`, `124/2,000자`.
- 폐기 ID는 §2의 목록을 따릅니다.

>
> 그곳에는 얼굴도, 이름도 같은  
> 또 다른 내가 살고 있었습니다.

**CPY-F01-014 — 장면 2 · 함선과 동면**

> 인류는 그들을 만나기 위해  
> 함선 ARCA를 지었습니다.
>
> 한 사람의 생애만큼 긴 항해를,  
> 사람들은 동면으로 건너기로 했습니다.

**CPY-F01-015 — 장면 3 · 소이와 JOY**

> ARCA 엔지니어 소이는  
> 매일 질문을 건네고 그 답을 모아
>
> 한 사람의 생애를 펼쳐 보이는 인공지능,  
> JOY를 ARCA에 실었습니다.

**CPY-F01-016 — 장면 4 · 이유**

> 또 다른 나를 만나면,  
> 우리는 어떤 이야기를 해야 할까.
>
> 오래 헤어진 사람을 다시 만날 때처럼,  
> 그들에게 들려줄 이야기가 필요합니다.

**CPY-F01-017 — 장면 5 · 질문과 기억**

> 동면 기간 동안 JOY는 하루에 한 번,  
> 잠든 당신에게 질문을 건넵니다.
>
> 떠오르는 기억과 감정이 모여,  
> 하나의 기억 조각으로 저장됩니다.

**CPY-F01-018 — 장면 6 · 출항**

> 이제 ARCA는 출항을 앞두고 있습니다.
>
> 탑승구가 닫히면,  
> 당신의 항해가 시작됩니다.
>
> 부디 ARCA에서 편안한 여행 되시길.

## 8. 의존 자료와 후속 문서 인계

### 8.1 법무·운영 자료

| 항목 | 현재 확정 가능한 범위 | 필요한 자료·완료 조건 | 영향 화면 |
|---|---|---|---|
| 서비스 이용약관 | 동의 Label·필수 여부·전문 열람·복귀 동작 | 승인 원문(익명 식별키 변경·미제공 시 수동 복구 불가 고지 포함, D-UI-098), 정책 버전, 실제 URL | F02·F30 |
| 개인정보처리방침 | 동의 Label·분석/삭제 고지의 의미·전문 열람 | 승인 원문, 정책 버전, 실제 URL, F31 문구 법무 감수 | F02·F30·F31 |

자료가 없다는 이유로 독립된 입력·저장·오류 문구 구현을 막지 않습니다. 다만 실제 링크를 placeholder 도메인으로 채우거나 이 문서의 요약을 법무 전문처럼 표시하면 안 됩니다.

### 8.2 API 소비 연결

화면별 OP는 [05 §4 · L126–148](./05_API_SPEC.md#4-15개-화면과-오퍼레이션-연결), 요청·결과·복구는 [05 §6 · L207–411](./05_API_SPEC.md#6-도메인-오퍼레이션-계약), 오류 확실성은 [05 §8.3 · L570–583](./05_API_SPEC.md#83-결과-확실성)에서 확인합니다. IX와 소비 화면은 §6의 참조를 사용하고 API 필드·검증 목록을 다시 복제하지 않습니다.

### 8.3 프런트엔드 구현 연결

라우트·Back·외부 복귀는 [06 §5 · L272–351](./06_FRONTEND_SPEC.md#5-라우팅과-앱-시작), cache 동기화는 [06 §6 · L353–411](./06_FRONTEND_SPEC.md#6-query-cache와-목록), 임시본·요청 추적·삭제는 [06 §7 · L413–451](./06_FRONTEND_SPEC.md#7-입력과-임시-보관)·[06 §8 · L453–551](./06_FRONTEND_SPEC.md#8-storage-journal과-command-복구)·[06 §9 · L553–602](./06_FRONTEND_SPEC.md#9-세션-닉네임과-삭제), 입력·Overlay·플랫폼은 [06 §10 · L604–659](./06_FRONTEND_SPEC.md#10-플랫폼-ui-분석-오류와-보호)을 따릅니다.

### 8.4 `07`·`08`과 시각 검증 인계

합성 입력 corpus는 [07 §3.5 · L61–76](./07_MOCK_SCENARIOS.md#35-합성-콘텐츠와-민감정보), 사건별 기대 결과는 [07 §11 · L181–309](./07_MOCK_SCENARIOS.md#11-이름-있는-시나리오-카탈로그), 검증 층·실기기·시각 비교는 [08 §3 · L50–76](./08_QA_AND_INTEGRATION.md#3-07-시나리오-실행-전략)·[08 §7 · L126–138](./08_QA_AND_INTEGRATION.md#7-입력-접근성-플랫폼-검증)·[08 §10 · L179–194](./08_QA_AND_INTEGRATION.md#10-성능-시각과-사용성)이 소유합니다. 에셋 권리·채택 상태는 [Asset Manifest · L1–10](../../design/assets/ASSET_MANIFEST.md)와 [02 §13.3 · L674–683](./02_DESIGN_SYSTEM.md#133-남은-시각-채택-작업)에서 확인합니다.

## 9. 앱인토스 공식 문서 확인

확인일은 2026년 9월 12일입니다. 아래 확인은 상호작용 결과의 근거이며 실제 import·adapter·config는 `06`에서 당시 설치 버전과 다시 대조합니다.

- [Storage](https://developers-apps-in-toss.toss.im/bedrock/reference/framework/%EC%A0%80%EC%9E%A5%EC%86%8C/Storage.html): `setItem`의 `Promise<void>`가 resolve되기 전에는 보관 성공 문구를 표시하지 않습니다. 토스 앱 삭제 시 네이티브 저장소도 삭제될 수 있으므로 임시본을 서버 기록처럼 안내하지 않습니다.
- [Clipboard](https://developers-apps-in-toss.toss.im/bedrock/reference/framework/%ED%81%B4%EB%A6%BD%EB%B3%B4%EB%93%9C/clipboard.html)·[권한](https://developers-apps-in-toss.toss.im/bedrock/reference/framework/%EA%B6%8C%ED%95%9C/permission.html): 쓰기에도 권한 상태와 실패가 있으므로 명시적 사용자 조작에서 요청하고 실패 시 read-only 원문 직접 선택을 유지합니다.
- [Navigation Bar](https://developers-apps-in-toss.toss.im/bedrock/reference/framework/UI/NavigationBar.html)·[화면 이동](https://developers-apps-in-toss.toss.im/bedrock/reference/framework/%ED%99%94%EB%A9%B4%20%EC%9D%B4%EB%8F%99/routing.html): 플랫폼 내비게이션과 앱 라우트·히스토리를 하나의 예측 가능한 계층으로 맞춥니다. 앱 내부 Back·Overlay·키보드 우선순위의 구현은 `06`에서 확정합니다.

## 10. Acceptance 추적

제품 합격 기준은 [docs/ARCA_MVP_ACCEPTANCE.md §3 · L48–150](../../docs/ARCA_MVP_ACCEPTANCE.md#3-핵심-qa-시나리오), 시나리오별 `Acc #`·API-V 추적은 [07 §11 · L181–309](./07_MOCK_SCENARIOS.md#11-이름-있는-시나리오-카탈로그)이 원본입니다. 필요한 기준 번호를 해당 파일에서 검색하고, 화면별 IX·CPY는 이 문서 §6~7에서 찾습니다. 동일 Acceptance 역추적 표를 중복 유지하지 않습니다.
